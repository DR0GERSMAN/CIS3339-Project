## 1. Purpose and scope

The Data Platform is used by nonprofit organizations and Community Health Workers (CHWs) to manage clients, services, events, and event attendance. The dashboard summarizes attendance and client ZIP-code counts. One shared MongoDB may serve multiple organizations; each deployed app instance is configured for one organization, and users must only see that organization's data. Viewers may read; editors may read and make changes.

Sprint 1 establishes a verified description of the supplied system, records its gaps, and proposes testable end-state behavior and a delivery plan. It does not claim that planned changes have been implemented. The scope below covers the frontend student-task guide, the core Project-README requirements, documentation, deployment, and bonus tests. The two guides reuse some task IDs, so their tracks are labeled separately throughout.

## 2. High-level architecture

The browser hosts a Vue single-page application. Vue Router selects views, Pinia holds login state, and the Axios client sends REST requests to the Express API. The API validates JWTs, applies route behavior, and uses Mongoose models to read or write MongoDB. JSON responses return through Axios to the Vue view, which updates reactive state and renders the result. The target architecture adds explicit role checks, organization-scoped queries, centralized errors, and reproducible initialization; several of these protections are missing or incomplete in the current code.

```mermaid
flowchart LR
	Person[CHW / editor / viewer] --> Browser
	subgraph Frontend[Vue 3 SPA in browser]
		Browser[Vue views and components]
		Router[Vue Router and navigation guard]
		Pinia[Pinia login/session state]
		Axios[Axios API client\nVITE_ROOT_API]
		Browser <--> Router
		Browser <--> Pinia
		Browser --> Axios
	end
	Axios -->|JSON REST + Bearer JWT| Express[Express / Node.js API]
	subgraph Backend[Backend]
		Express --> Cors[CORS + JSON middleware]
		Cors --> Auth[JWT authentication\nrole authorization (target)]
		Auth --> Routes[Client / event / service / org / user routes]
		Routes --> Scope[Organization-scoped query helper (target)]
		Scope --> Mongoose[Mongoose models and schemas]
	end
	Mongoose --> Mongo[(MongoDB\norg, users, clients, events, services)]
	Mongo -->|documents / aggregate results| Mongoose
	Mongoose --> Routes
	Routes -->|status + JSON| Axios
	Axios --> Browser
```

**Current implementation notes:** Frontend files are under [frontend/src](frontend/src); the Vite app and its plugin setup are in [frontend/src/main.js](frontend/src/main.js). The API client reads `VITE_ROOT_API` in [frontend/src/api/api.js](frontend/src/api/api.js). Express mounts the route modules and connects Mongoose in [backend/app.js](backend/app.js), while schemas/models are in [backend/models/models.js](backend/models/models.js). The current server allows CORS from `*`, has authentication middleware but no reusable role authorization middleware, and does not consistently scope all queries to the authenticated user's organization. Those are gaps, not intended final behavior.

## 3. Current-template user-flow diagrams

The diagrams describe available template flows and identify where required behavior is incomplete. A workflow depicted as current does not imply its security or error behavior already meets the target.

### Flow A — Sign in, browse clients, and open a record

```mermaid
flowchart TD
	A[Open app] --> B{Pinia says logged in?}
	B -- No --> C[Router sends protected route to Login]
	C --> D[Enter username and password]
	D --> E[POST /users/login]
	E --> F{Credentials valid?}
	F -- No --> G[Show login error]
	F -- Yes --> H[Receive JWT; save token and set Axios header]
	H --> I[Open Find Client]
	B -- Yes --> I
	I --> J[GET /clients with Bearer token]
	J --> K[Render client rows]
	K --> L[Select a row]
	L --> M[Open /clientdetails/:id]
	M --> N[GET client by ID and render details]
```

**Current gaps in this flow:** startup does not restore a saved token to the Axios header and Pinia state; the current list endpoint queries `find({})` without a tenant filter; a failed request may be shown as an object instead of a readable message. The router checks authentication only and does not protect editor-only form routes by role.

### Flow B — Find an event and register a client

```mermaid
flowchart TD
	A[Authenticated user opens Find Events] --> B[GET /events or search events]
	B --> C[Select event and open event details]
	C --> D[Load event and attendee / eligible-client information]
	D --> E{User is editor?}
	E -- No --> F[Viewer can inspect; no registration action should be permitted]
	E -- Yes --> G[Choose client and register]
	G --> H[PUT /events/register with event and client IDs]
	H --> I{Event and client exist in user's organization?}
	I -- No --> J[404; do not modify data]
	I -- Yes --> K{Already registered?}
	K -- Yes --> L[200 Already registered; no duplicate]
	K -- No --> M[Add attendee and return success]
	M --> N[Refresh event / attendee display]
```

The template already models event attendees as client IDs on an event and has register/deregister endpoints. The expected viewer denial, same-organization checks, duplicate response, and safe deregistration behavior are specified in the target contract; current route behavior does not satisfy all of them.

## 4. Trace of one existing request, view to database and back

**Example:** load the client list when `findclient.vue` mounts.

1. In [frontend/src/views/findclient.vue](frontend/src/views/findclient.vue), the `mounted()` hook calls `loadData()`.
2. `loadData()` calls `getClients()` from [frontend/src/api/api.js](frontend/src/api/api.js). The function sends `GET clients` through the Axios instance whose base URL is `import.meta.env.VITE_ROOT_API`; the token is supplied in the shared `Authorization` header after login.
3. [backend/app.js](backend/app.js) mounts the client router at `/clients`. The router's `GET /` handler in [backend/routes/clients.js](backend/routes/clients.js) invokes JWT authentication middleware, then calls `clients.find({})`.
4. `clients` is the Mongoose model created from `clientDataSchema` in [backend/models/models.js](backend/models/models.js), mapped to MongoDB's `clients` collection. MongoDB returns matching documents to Mongoose.
5. The route serializes the result as JSON. Axios resolves with the response; `getClients()` returns `response.data`; `loadData()` assigns that array to `this.clients`; Vue renders the rows in the table.

**Observed behavior / risk:** this is a real end-to-end request path, but `find({})` is not organization-scoped. Also, the view catches and passes the error object directly to the toast. The path is useful as a tracing example, not as an acceptable security or error-handling pattern. The current `GET /clients` route is protected by authentication middleware, but the JWT does not currently carry the organization claim needed by the target shared tenant filter.

## 6. Proposed testable functional specification

The following is the proposed end state. It should be approved by the team before implementation; any agreed deviation should be recorded in an issue/PR and this specification updated.

### User roles and application behavior

| ID | Requirement | Acceptance test |
|---|---|---|
| FS-01 | Users can log in with valid credentials as viewer or editor; invalid username and invalid password yield the same public message. | Exercise both invalid cases and verify identical status/message; valid demo accounts receive a usable session. |
| FS-02 | A valid unexpired token restores Axios authorization and Pinia role/login state after refresh; expired, malformed, or tampered tokens are cleared without an application crash. Logout clears token, header, and Pinia state. | Login, refresh a protected route, then test expired/corrupt storage and logout; confirm final state and route behavior. |
| FS-03 | All protected data views require authentication. Editor-only UI routes and all server-side mutations require the editor role; the server is authoritative. | Directly navigate as viewer to each editor form and submit a mutation request as viewer; redirect on UI and return HTTP 403 from API. Editor mutation succeeds when otherwise valid. |
| FS-04 | Every client, event, and service read/write is restricted to `req.user.orgId`, including search, detail, aggregate, attendance, registration, and deletion paths. | Seed two organizations; authenticate as A and prove A cannot read, update, delete, register, or infer B's records (not found where specified). Repeat as B. |
| FS-05 | Client, event, and service CRUD/search flows remain usable with existing data shapes and validation; CHWs can view records and editors can make permitted changes. | Run create/read/search/update/delete cases per entity, including validation and business-rule failures; confirm UI refreshes to current results. |
| FS-06 | The event attendance workflow registers/deregisters only same-organization client/event pairs and is idempotent. | First registration creates one attendee; repeating returns HTTP 200 `{ "message": "Already registered" }` and leaves exactly one; deregistering a non-attendee returns HTTP 200 `{ "message": "Not registered" }`; cross-org/missing pair returns 404. Both endpoints require auth and editor role. |
| FS-07 | Client/event/service lists and dashboard expose separate loading, success, empty, and failure states. Retry repeats the same request; failures display a short human-readable message, never `[object Object]`. | Simulate slow, empty, successful, rejected, and offline API cases; verify correct visible state and retry. Confirm Axios interceptor normalizes failures and clears/redirects on 401. |
| FS-08 | Shared `DataTable` sorts each configured column ascending/descending/unsorted, paginates 10 rows, reports displayed range/total, handles no results, and resets/clamps page after search/data changes. | Use at least 15 rows for each list; test sort cycle, pages, search while on later page, empty set, and no stale rows. |
| FS-09 | Frontend refactor preserves login, role display, validation, CRUD, search, chart data, date display, and route-param behavior; charts update on prop change and clean up on unmount. | Regression-test relevant flows, run without Vue warnings/errors, update chart props, and navigate away/back repeatedly with no accumulated chart instance/listener. |
| FS-10 | Express returns consistent `{ "error": "Human readable message" }` responses for validation/not-found/unexpected failures with statuses 400/404/500 and no stack/raw DB details; `GET /health` works without authentication and reports app/database state. | Exercise all three error classes and health while DB connected/disconnected; inspect response shape and absence of sensitive details. |
| FS-11 | `npm run db:init` validates config, hashes passwords, creates the required org, viewer/editor, representative clients/services/events and at least one registration, plus required indexes; repeat runs do not duplicate data or delete existing data. | Run against a disposable empty DB, verify login and seeded relationships, rerun and compare counts/IDs; misconfiguration must exit nonzero with useful diagnostics. |
| FS-12 | Production frontend installs, builds, and serves using documented `VITE_ROOT_API`; static hosting supports nested-route refresh and configured backend CORS. | From clean dependencies run `npm run build`, then preview/serve `dist`; open/refresh a nested route, test API connectivity, and follow the documented hosting fallback setup. Demo must use production build. |
| FS-13 | UX and accessibility meet the specified baseline: 375px usable responsive navigation; keyboard-operable table rows; meaningful logo alternative text and portable path; `lang="en"`; associated labels; accessible confirmation modal with cancel, focus trap, and Escape. | Test at 375px, keyboard-only navigation, screen-reader/name inspection, delete confirm/cancel network behavior, and record before/after Lighthouse or axe findings plus deferred items. |
| FS-14 | New developer can reproduce setup, initialization, test/build, and deployment from README and documented environment examples; no personal or production secrets enter source/report. | Follow instructions in a clean checkout using a dedicated course/test database; verify `.env.example`, run scripts, demo accounts, and documented known limitations. |

**Verification plan:** Automated unit/component tests should cover `formatDate`, `useApi` success/failure, `SearchBar` payload, and router role guard. Backend/API integration tests should cover viewer 403/editor success, tenant isolation, registration idempotency, central error shapes, and health. Use isolated disposable test data, not the grading/production database. Then run frontend lint/test/build and documented API/integration checks, followed by manual role-based workflows and deployment-preview smoke tests. Record exact commands and results in the README/CI output. Bonus tests are proposed and are not represented as already configured.

### Proposed ownership model

- **Facilitator / requirements owner:** meeting notes, acceptance criteria, issue board, Canvas deadline confirmation, and final scope decisions.
- **Frontend owner:** Vue migration, session/UI behavior, reusable components, accessibility, responsive layout, frontend build.
- **Backend/security owner:** Express middleware, JWT claims, organization isolation, error/health behavior, registration contract, CORS.
- **Data/setup owner:** Mongoose constraints, safe/idempotent seed script, environment examples, onboarding instructions.
- **QA/integration/deployment owner:** test strategy, isolated test data, acceptance evidence, build/preview/hosting smoke tests, demo checklist.

For a smaller team, combine roles explicitly. Every significant implementation PR should list an author, an independent reviewer, linked acceptance criteria/issues, and test evidence. Security and tenant-isolation changes require review by someone other than the author. If these dates conflict with Canvas, Canvas takes precedence and owners should rescope openly rather than silently omit acceptance criteria.
